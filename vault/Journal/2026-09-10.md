## Problems Encountered

- A `print` call with a line-wrapped `f"…"` spanned two physical lines → `SyntaxError: unterminated f-string literal`. 
- `ruff format` kept re-expanding hand-wrapped `+` chains into one-operand-per-line blocks and re-adding "magic trailing commas" — fighting it by hand was a losing game.
- `ruff check` flagged `f"{str(e)}"` (rule RUF010): calling `str()` inside an f-string field is redundant.
- Added the README sample as a ` ```ansi ` code block expecting GitHub to render it in color. GitHub only interprets `ansi` blocks in issue / PR / discussion comments, not in Markdown files, so the rendered README showed raw escape codes.

---

## Solutions

- Kept each string literal whole and broke the line only between tokens (after `+`), inside the `print(...)` parentheses.
- Converted the messages to single f-strings so there was no `+` chain to reflow, and accepted `ruff`'s output as the project style.
- Replaced `{str(e)}` with `{e}`.
- Reverted the sample to a plain code block; the color-legend table below it carries the meaning.

## Concepts Learned

- A single- or double-quoted string cannot contain a raw newline; only a triple-quoted string can.
- `argparse` turns `sys.argv` into an object with named fields; like a struct / UDT in ST. `parse_args()` is the call that actually reads the command line and applies the rules; `add_argument` only registers them.
- Function arguments bind by position, not name: `check_host(host, args.port, args.timeout)` fills the second parameter regardless of what it is called.
- f-strings replace concatenation: `f"{a} | {b}"`, not `a + " | " + b`.
- Docstrings are kept by the interpreter as `__doc__` and rendered by tools (often as Markdown); `#` comments are discarded at parse time.
- Adopt the formatter early. Hand-formatting to match it wastes time and introduces real bugs.
- `except` clauses are matched top to bottom; a broad class listed before its subclasses hides them.
