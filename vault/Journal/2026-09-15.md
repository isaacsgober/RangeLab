## Solutions

- `ssh -tt` gave `appliancesh`'s `shell` a terminal; `keyboard-interactive` worked for ESXi.
- Cleaned up through the REST API: `DELETE /api/vcenter/host/{id}`, then `POST /api/vcenter/host` with the host folder and root credentials.
- Used `service-control` for the masked VCSA services.
- Read Envoy's response flags (`UH`, no healthy upstream) and dnsmasq's own query log to locate where resolution failed.
- `nslookup -debug -type=AAAA <name>. 10.10.10.2` showed the `rcode` directly: NXDOMAIN for AAAA, NOERROR for A.
- `host-record` makes the embedded dnsmasq answer lab names itself, so it never forwards them and never caches the bad AAAA answer.
- Tested the AAAA theory before finalizing the docs, corrected the root cause, then rewrote ISA-5 with a comment listing what the first version got wrong.
- Waited out Windows Time's startup dispersion. At a 64 s poll it halved with every sample (8.16 → 4.16 → 2.16 → 1.15 → 0.64 → 0.38 s); ansible01 then stepped +13768.6 s and its clients followed.
- Restarted ntpd on esxi01, since ESXi's ntpd only accepts a large correction at startup.
- Queried NTP servers directly for real time instead of trusting an HTTP header.
- The SSH drops were OpenSSH 9.9's per-source penalties (`penalty: exceeded LoginGraceTime` in the logs). They cleared on their own once the penalty expired.
- Chose shutdowns over suspends, with autostart handling the VMs, rather than tuning NTP to recover faster from a suspend.
- Queried every record type, not just A and AAAA, plus a made-up subdomain. The pattern was clear: only A worked, and subdomains matched too.
- Read dnsmasq's own manual on the server (`zcat /usr/share/man/man8/dnsmasq.8.gz`). Its `--address` section describes the 2.86 behavior change.
- Ran `dcui` inside an SSH session to capture its screen. Then tested where its hostname comes from with a reversible `/etc/hosts` change and a `tcpdump-uw` capture.

## Concepts Learned

- **NXDOMAIN means the name doesn't exist, for every record type,** and resolvers treat it as final. A name with an A record but no AAAA record should get `NOERROR` with an empty answer.
- **Negative caching** stores that answer. `neg-ttl=3600` turned one wrong AAAA reply into an hour of failed A lookups, which made the fault look intermittent.
- **Programs resolve names differently.** `getent` goes through NSS and systemd-resolved; Envoy reads `/etc/resolv.conf` and queries those nameservers itself. One working says nothing about the other.
- On the VCSA, `/etc/resolv.conf` lists `127.0.0.1` (the embedded dnsmasq) first. systemd-resolved's own stub is `127.0.0.53`.
- Envoy's access-log response flags explain a 503: `UH` means no healthy upstream, and an empty upstream host means no endpoint was ever chosen.
- The top-level error ("Unable to push CA certificates and CRLs") was accurate the whole time, just shallow. The cause was in the component logs.
- A "harmless" line deserves a second look. The trailing AAAA NXDOMAIN on every `nslookup` was the bug.
- Fixing something real doesn't prove it was the blocker. The CPU, the stopped services, and the certificate were all genuine problems fixed before the add worked; only a before-and-after test separates cause from coincidence.
- Verify before documenting. The first write-up went out before the AAAA test and had to be corrected.
- **Suspending esxi01 freezes everything nested inside it.** Workstation catches its own VMs up on resume; the VMs inside ESXi get nothing.
- **A time server with no upstream only keeps the lab consistent while it keeps running.** `local stratum 10` kept every node agreeing, right up until the server froze and everything followed it.
- **NTP clients judge a source by how uncertain it says it is, not just whether it answers.** chrony drops sources over 3 s of root distance and ntpd over 1.5 s. Windows Time starts out claiming about 8 s and settles within minutes.
- **`makestep`:** by default chrony only steps the clock right after it starts and slews after that. A 3.8-hour slew would take about two days; `makestep 1.0 -1` allows a step at any time.
- **ESXi's ntpd (`-g`)** allows one large correction at startup, and after that refuses anything over 1000 s.
- A clean boot beats recovery. A booting VM reads its virtual hardware clock and starts NTP with no stale history.
- **`address=` is a rule for a domain; `host-record` defines a host.** `address=/esxi01.rangelab.local/10.10.10.10` answers A queries for that name and every subdomain, and nothing else. `host-record` makes the name exist, so a query for a type it lacks gets an empty `NOERROR`.
- **Prove a source fix by removing the workaround.** With vcenter01's `host-record` lines still in place, the dnsmasqhost fix would never have been tested.
- **Change one input at a time.** Two explanations fit the DCUI's short name. Changing the hosts file, then watching DNS, separated them.
- **"Correct password rejected" often means a lockout.** `pam_faillock` refuses a locked account whatever password is typed. Check `faillock --user <name>` before doubting the password.
